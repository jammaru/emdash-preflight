# Architecture

EmDash Preflight is a sandboxed EmDash plugin. `src/plugin.ts` is the runtime entry point generated by the official plugin CLI scaffold.

```text
content:beforePublish / content:beforeSchedule
                    │
                    ▼
              policy settings
                    │
                    ▼
       central rule registry + evaluator
           │                    │
           ▼                    ▼
      stable issues        bounded lookups
           │                    │
           └─────────┬──────────┘
                     ▼
             issue storage + result
              │        │        │
              ▼        ▼        ▼
           hook     Block Kit    MCP
```

## Runtime boundaries

- Pure policy, rule, fingerprint, and result code lives under `src/engine`, `src/policy`, and `src/rules`.
- EmDash capability calls are adapted in `src/emdash/context.ts`.
- `src/storage/issues.ts` owns issue persistence and indexed filtering.
- The sandbox runtime never imports Node.js built-ins and never makes outbound requests.
- MCP tools and plugin routes are read-only with respect to site content. The only write route saves Preflight's own policy setting; issue writes remain plugin-owned storage.

## Publish path

The before-publish and before-schedule hooks call the same policy loader, evaluator, and issue persistence path. The policy hook event supplies the pending content snapshot and identifies its source. Preflight does not need content write or publish authority. EmDash also invokes the publish policy for scheduled content when it becomes due, so the entry is checked against current policy and referenced content at publish time.

Observe mode records completed findings and allows publication. Enforce mode blocks error findings. Invalid policy data or an incomplete evaluation blocks in Enforce mode; the cancellation reason explains that the check could not complete without exposing runtime details. In Observe mode, incomplete checks are logged and do not alter publication.

## Bounded work

The rule adapter permits no more than eight planned EmDash lookups per entry. Media and reference rules each inspect at most two unique targets. Batch audit accepts a cursor and evaluates at most 25 published entries per call. Each entry's cross-resource lookups remain bounded independently. Storage work is scoped to the affected entry and does not scan the site during publication.

## Storage

The plugin uses `ctx.settings` for versioned policy data and one indexed `issues` collection for current findings. An issue's unique key is its stable fingerprint. On a complete recheck, Preflight updates still-open issues and deletes resolved ones. Incomplete checks do not clear findings.

## Admin and agents

The dashboard and saved-entry panel return host-rendered Block Kit. The panel reads the saved entry identified by host-attested `routeCtx.ui`; it does not receive unsaved editor values. MCP tools expose structured results, issue pages, rule explanations, and cursor-based audit. Agents fix content using normal EmDash tools, then recheck.
